# Database performance at growing cardinality

Use the project's database engine and version. PostgreSQL examples below are illustrative; adapt placeholder syntax, indexes, tuple comparisons, and migration behavior to the actual driver and engine. Consult official engine documentation for version-sensitive features.

## Inspect the existing access path

Read the schema, existing indexes, SQL generated by the ORM, and all callers. Record query frequency, rows returned versus examined, tenant distribution, filter selectivity, sort order, and write frequency. A 50GB database could contain one large table or thousands of small ones; optimize the actual workload.

Begin with a nonexecuting plan where available. An execution plan with analysis executes the statement: use a representative authorized environment and bounded queries. For PostgreSQL, `EXPLAIN (ANALYZE, BUFFERS)` reports actual execution and buffer activity. Even read queries can be expensive or invoke side effects through functions; writes can alter data. A transaction rollback does not reverse every external effect.

Look for estimate/actual row mismatches, repeated inner loops, rows removed by filters, large sorts, disk spills, heap fetches, lock waits, and I/O. Do not treat every sequential scan as a defect: broad scans can be appropriate. Check statistics and data skew before forcing a plan.

## Remove expensive work

- Project only needed columns; avoid `SELECT *` on application hot paths when large unused fields exist.
- Apply tenant and authorization filters inside the query, including related-object queries.
- Use set-based joins, aggregation, or bounded batches for N+1 reads. Paginate parents before expanding one-to-many children so joins do not corrupt page cardinality.
- Keep predicates index-friendly where semantics allow: compare stored timestamps against typed half-open bounds rather than wrapping every row in a date conversion. Preserve the caller's time zone and boundary behavior.
- Prefer existence checks when only existence matters; do not count or fetch every match.
- Avoid mandatory exact counts for every page when the contract permits a separate or optional count. Preserve exact counts when explicitly required.
- Bind values through driver parameters. Validate page sizes, cursor types, and allowlisted dynamic sort identifiers.

## Select indexes deliberately

Design against the complete predicate and ordering. For a B-tree, equality on leading columns followed by range/order columns is a useful starting point, not an engine-independent law. Mixed sort directions, ranges, skew, optional filters, and engine features change what works.

Example access pattern: one tenant's orders sorted newest first, ordered by a non-null timestamp and unique ID. A candidate PostgreSQL index is:

```sql
CREATE INDEX CONCURRENTLY orders_tenant_created_id_idx
ON orders (tenant_id, created_at DESC, id DESC);
```

First check existing indexes, real plans, and the framework's migration behavior. PostgreSQL concurrent index creation cannot run inside a transaction block; it adds workload, can wait on transactions, and failed builds can leave invalid indexes. Do not run this illustrative statement blindly on a live database.

Additional status filters may favor a different index depending on selectivity and workload. Partial and covering indexes can help specific patterns, but parameterized predicates, engine rules, visibility, index width, and write amplification matter. Do not index every column or include large payloads. An index-only scan is not guaranteed merely by covering the requested columns.

## Stable, bounded pagination

For deep sequential pages, use a keyset when the contract allows it. With non-null keys and descending order:

```sql
SELECT id, created_at, total_cents
FROM orders
WHERE tenant_id = $1
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT $4;
```

Use a separate first-page query without the cursor predicate. Derive the cursor from the last returned row; validate it and bind it to the filter/order context. Keep tenant identity from trusted authentication. Fetch at most a validated page limit, optionally plus one row to report whether a next page exists.

The unique tie-breaker prevents dropping rows sharing timestamps. Null or mutable ordering keys need explicit semantics and a compatible predicate. Keyset browsing does not inherently supply snapshot isolation: inserts, deletes, and updates can still affect subsequent pages. Use a snapshot or defined watermark only when the product requires a consistent traversal.

Large offsets still require processing skipped rows. Keysets do not provide arbitrary page-number jumps; preserve that requirement or explicitly provide a compatible alternative rather than silently changing the API.

## Transactions, writes, and migrations

Use constraints for uniqueness and referential integrity. Prefer atomic updates over read-then-write races; preserve isolation and idempotency. Batch writes within driver parameter limits and acceptable transaction/lock/WAL budgets. Keep batch size bounded and adjustable where measurements require tuning.

Plan backfills in resumable chunks with a stable key and progress checkpoints. Evaluate online/concurrent DDL support, replication lag, free disk, lock timeouts, and rollback behavior. Prepare the migration before deployment; follow environment authorization for execution. Partitioning, replicas, denormalization, and sharding need workload evidence and an operational plan. Replicas also require consistency and read-after-write decisions.
